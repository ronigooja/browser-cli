# Safari Web Extension probe

Development-only, isolated from the CLI and MCP. The Swift companion and embedded Safari Web Extension probe **transport, profile binding, website authorization, focus, and zero-window recovery**. Only the fixed `https://example.com/` fixture is supported. The probe does not extract text, expose credentials, or use Apple Events, Accessibility, TCP, or fallback opens. Use a disposable Safari test account/profile set, not an existing browsing session.

## GitHub-hosted macOS build

Dependencies: Git checkout and the full Xcode toolchain (Xcode 16+ with macOS SDK; macOS deployment target 14.0 for both targets). No package manager or generated project. A GitHub-hosted `macos-15` runner has Xcode and Safari; use the [runner image inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-Readme.md) to select/pin an available Xcode if needed. This is a build and protocol-gate check, **not** a Safari integration test. From the checkout root on that runner:

```sh
xcodebuild -project safari-prototype/SafariProbe.xcodeproj -scheme SafariProbe \
  -configuration Debug -destination 'platform=macOS' \
  -derivedDataPath "$RUNNER_TEMP/safari-probe" CODE_SIGNING_ALLOWED=NO build

app="$RUNNER_TEMP/safari-probe/Build/Products/Debug/SafariProbe.app"
test -f "$app/Contents/PlugIns/SafariProbeExtension.appex/Contents/Resources/manifest.json"
"$app/Contents/MacOS/SafariProbe" verify-gate
```

`verify-gate` invokes the same Swift authorization logic as the native handler, with synthetic inputs. It covers profile and nonce mismatches, expiry, single claim/result, read-only pull, and transport separation for the window qualification. It does not use the mailbox, dispatch, or Safari. Run JavaScript qualification mocks with `node --test safari-prototype/window-qualification.test.js` on Linux.

### Signing and deployment

- The unsigned CI build is for compile/packaging checks and is not expected to exercise the protected group mailbox. For a live test, build/sign both targets with the **same** Apple Development team. With a runner already provisioned with a usable certificate and any required profiles, use the same command without `CODE_SIGNING_ALLOWED=NO` and pass `DEVELOPMENT_TEAM=<team-id>`. The default `PROBE_APP_GROUP` expands to `<team-id>.com.ronigooja.agentbrowser.safariprobe`. Apple documents that macOS groups in this form do not need separate group registration; it does not guarantee entitlement acceptance, provisioning, or compatibility of this build with a particular signing identity. Before using the build, inspect the host and `.appex` with `codesign -d --entitlements :-` and verify matching app-group and sandbox entitlements; inspect both bundled `Info.plist` files for the matching `ProbeAppGroup` value. Signing, group access, and Safari registration are not yet verified.
- At base `9da8e7f`, Actions were enabled and the remote reported zero workflows, runs, releases, and repository-level Actions secrets. A read-only identity check on the workstation found an Apple Development identity, but no Developer ID signing identity; this does not establish runner access, provisioning, or notarization capability. No credential was exported, and no workflow or release was created by this prototype.
- Apple's [distribution guidance](https://developer.apple.com/documentation/safariservices/distributing-your-safari-web-extension) allows Mac App Store signing or Developer ID signing plus notarization. It also documents testing unsigned extensions behind an explicit Safari Developer setting. That setting is **not** a substitute for a valid signed app group, and the temporary folder-only setup does not install this native host. No user settings are changed automatically.

## Protocol and limits

Apple's [native messaging guide](https://developer.apple.com/documentation/safariservices/messaging-between-the-app-and-javascript-in-a-safari-web-extension) documents `connectNative` for host notifications and `sendNativeMessage` for separate requests into the native handler. [Host dispatch](https://developer.apple.com/documentation/safariservices/sfsafariapplication/dispatchmessage(withname:toextensionwithidentifier:userinfo:completionhandler:)) has no profile argument and its completion supplies only an error; it can launch Safari if necessary. A non-error completion is **not** a JavaScript reply or evidence that any particular profile received the message. [`SFExtensionProfileKey`](https://developer.apple.com/documentation/safariservices/sfextensionprofilekey) is Safari-supplied on JavaScript-to-native requests on macOS 14+/Safari 17+; the handler rejects missing UUIDs instead of inventing a default profile. The key can also designate a Safari web app, so use the popup in Safari itself to label test bindings; a UUID alone does not identify a browser profile by name.

1. In push mode the containing app publishes a five-second request in its [App Group](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups) mailbox. Dispatch carries only a fresh random request UUID.
2. A receiving background instance sends the UUID and its own random in-memory instance UUID to the native handler. Discovery only records Safari's profile UUID and the instance UUID. A bound request returns its operation and flags **only after** the handler checks both values, locks the request, and atomically marks it claimed.
3. JavaScript checks the grant's nonce and expiry before the permitted operation and posts the result via native messaging. The handler rechecks Safari's profile UUID, nonce, expiry and single-result rule. The host reports dispatch and verified receipts separately, collecting for the full lease so a late negative receipt has a chance to arrive. It does not retry operations. A missing or expired result after claim leaves the outcome unknown; do not blindly repeat a write.

The mailbox is a private UID-owned directory inside the app group, with random request subdirectories, non-symlink locking/reads, bounded state and reply sizes, and cleanup on normal exit. If the host is killed, expired mailbox files can remain under the group path; they cannot be used by the handler to claim or return a result after expiry under a stable clock. This is local owner-scoped IPC, not protection from malicious software running as the same user, a compromised extension, or administrator access. The host checks that Safari is running and finished launching before dispatch; Safari can still quit between check and dispatch, and actual launch/focus behavior must be measured. If a nonpersistent background instance restarts, the nonce changes; a stale binding fails and the operator must rediscover, never silently rebind. No promise is made that a dormant profile will run, that dispatch fans out, or that dispatch succeeds with zero UI windows.

## Opt-in pull: read-only transport and focus proof

Use the signed, registered app in the disposable test session described below. Start with one explicitly named regular profile and private extension access off. Open a normal window; do not grant site access for this test. The manifest still lists only `https://example.com/*`, and `pull windows` does not read URL fields or inject, but requests populated windows to collect tab diagnostics; the browser may internally request access while populating them. The popup shows whether the alarms API is available and whether the native push port is open.

1. In the explicitly named profile, open the **Safari Probe Identity** popup. Record its Safari UUID and current instance nonce, then click **Arm one pull (60s)**. Wait for the popup to confirm its scheduled time, close it, leave Terminal frontmost, and promptly run:

   ```sh
   probe='/absolute/path/to/SafariProbe.app/Contents/MacOS/SafariProbe'
   "$probe" pull discover
   ```

2. Arm again from the same profile and repeat with `"$probe" pull windows "$PROFILE_UUID"`. Use the UUID from the confirmed profile, not an inferred default. The read targets that UUID but needs no prior nonce: the matching background instance is bound at claim, and only that instance can return the result. Push operations still require the original UUID **and** nonce. This arm never authorizes writes or inspection.
3. For a negative check, arm from the default context where identity reports `safari_profile_missing`, and repeat `pull discover`. If the alarm reaches native code without metadata, expect that same status in `pullObservations`, with no receipt, binding, or grant. `no_verified_reply` without observations does not distinguish a missed alarm, popup setup that failed, a suspended/quit browser, or native messaging/mailbox failure. Repeat with the intended no-window setup separately; do not open a window mid-lease to help it succeed.
4. Require `transport: "pull"` and `dispatch: "not_called"`, plus a verified receipt and (for `windows`) `result.status: "ok"`. Compare `frontBefore`, `frontAfter`, and `activationEvents` with what was independently observed. Compare `backgroundStartedAt` with `publishedAt` and `alarmScheduledAt` (Unix seconds), and the new nonce with the pre-arm popup nonce to distinguish a restarted background from a warm one. These signals are observational: they do not prove which Safari process ran or guarantee that brief focus changes were captured. In an empty snapshot, `windowClassification.returned: 0` means `getAll` returned nothing; nonzero with `windows: []` means the returned objects failed strict regular-window classification. Missing properties are counted without emitting URLs or private window details; uncertainty does not relax the filters.
5. Use the popup's **Use push** control before a push comparison; it clears the pending alarm and reconnects the old transport. Take a fresh popup nonce for bound push requests. Do not keep a popup or background inspector open during the primary pull run.

The pull host atomically publishes one active request in a separate owner-scoped App Group mailbox and never calls Safari dispatch. The popup opts in persistently to no push port and schedules a single browser-owned alarm per button press. The primary test invokes `sendNativeMessage` only from that alarm: no polling timer, recurring alarm, network endpoint, automatic rearm, or push fallback. The host collects for the full lease; `pull --wait-seconds N discover` and `pull --wait-seconds N windows UUID` override the default 90-second experiment budget (1–180 seconds). Start the host before the alarm fires; a pull with no pending lease is not held open. A killed host can leave an expired request and pointer behind; the next host publishes a new UUID, never replays the old request.

**Optional warm-context comparison.** Set `PROFILE_UUID` ahead of time. Click **Arm warm test (120s)** once in the same profile, wait for confirmation, close the popup, return to Terminal, and run this short read-only sequence without reopening Safari between requests:

```sh
"$probe" pull --wait-seconds 8 discover
"$probe" pull --wait-seconds 8 windows "$PROFILE_UUID"
"$probe" pull --wait-seconds 8 windows "$PROFILE_UUID"
```

The already-running background polls after one second, then one second after each completed native exchange, for at most 120 seconds and at most 120 polls; it does not restart polling after an unload. Expect the first `warm_poll` observation about one interval plus IPC/browser scheduling after publication if the context stays alive; there is no latency or liveness guarantee. For the accepted read, subtract `publishedAt` from `receivedAt` on the `claimed` observation and from `resultReceivedAt` to measure claim and round-trip latency separately from the CLI's collection window. Compare activation evidence and nonce across commands. To test the 60-second fallback in a separate arm, use `"$probe" pull --wait-seconds 90 windows "$PROFILE_UUID"` right after returning to Terminal. `wake: "alarm"` on the **claim**, rather than on a later `already_claimed` observation, shows the fallback took over; if warm polling remained live this run may still claim via `warm_poll`. A short lease that times out before the alarm is not replayed by the alarm. Do not interpret the warm comparison as proof of idle wake, even with no Safari activation observed.

[MDN compatibility data](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/alarms.json) lists the named alarms API in Safari 14+. Current WebKit source [clamps short alarms to 30 seconds outside testing](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/Shared/Extensions/WebExtensionConstants.h), [wakes the background for `onAlarm`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/Extensions/API/WebExtensionContextAPIAlarms.cpp), and [schedules nonpersistent background unloading on a 30-second delay outside its test runner](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/Extensions/WebExtensionContext.cpp). These are source-code observations, not promises about a particular Safari release or an inactive profile. No alarm persistence across Safari restarts is assumed. The 60-second arm is meant to give the background time to unload and to avoid relying on the shortest alarm interval.

**Production boundary.** Keep the authenticated mailbox/claim/result protocol separate from the wake mechanism and set deadlines per caller. A one-shot alarm per call is not suitable for sequential MCP requests. A bounded batch of already authorized reads could amortize one browser wake, but not later requests after the background sleeps. An explicit extension action could trigger an immediate pull while Safari is in use, or start a bounded active session as above, but neither proves unattended idle delivery. An App Group file does not wake JavaScript. Apple's documented host dispatch ensures Safari launches if necessary, and foreground activation was observed in the prior push scenario; it is not a silent fallback.

[MDN manifest compatibility data](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/background.json) lists macOS Safari persistent background support from 14.1 for MV2 only; [Apple's guidance](https://developer.apple.com/documentation/safariservices/optimizing-your-web-extension-for-safari) requires a nonpersistent page or worker in MV3. If the current target Safari accepts and keeps an MV2 background alive, a separately built, explicitly selected MV2 adapter could invoke this same native pull without a server, network, content page, or host dispatch. Do not change the registered MV3 build to test it. A separate live build must establish acceptance, persistence when idle and with no windows, profile UUID availability and isolation, bounded foreground-free latency, and deployment/distribution viability. Consider idle resource cost and MV2 longevity; compatibility data alone cannot establish those properties. No unattended low-latency, no-focus transport is established by this probe.

## Zero-window qualification (separate consent, no dispatch)

[MDN compatibility data](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/windows.json) lists Safari support for `windows.create` with `focused`, `incognito`, `type`, and `url`. The consulted [WebKit source](https://github.com/WebKit/WebKit/blob/04ab78ad6a9351b909ee026ad7b911d667ca4ca0/Source/WebKit/UIProcess/Extensions/Cocoa/API/WebExtensionContextAPIWindowsCocoa.mm) forwards these to the [embedding application's delegate](https://github.com/WebKit/WebKit/blob/04ab78ad6a9351b909ee026ad7b911d667ca4ca0/Source/WebKit/UIProcess/API/Cocoa/WKWebExtensionControllerDelegate.h) with the calling extension context. Neither the public configuration nor the JavaScript API offers a Safari profile selector. `SFExtensionProfileKey` authenticates the requesting context, not the profile of the returned window. The sources don't establish Safari's handling when there are no windows. The unpopulated inventory avoids WebKit's tab-URL permission collection but cannot see windows outside the extension's view.

1. On each target macOS/Safari build, use the signed, registered probe in a separate disposable GUI session. Use two distinguishable named regular profiles A and B, no web apps or private windows, private extension access off, and `example.com` preapproved. Independently confirm each profile in Safari. Before a zero-window attempt, also run the **read-only** warm/one-shot tests above after closing the last window, separately for immediate and idle cases. For production liveness, test the **signed production MV2** build independently: run its read-only `status` and `find` with a window as positive controls, then at zero windows immediately and after at least two minutes idle (or the longest intended idle interval if longer). Run both for the exact selected UUID; require repeated `ok` within the normal request budget, and `find` with no tabs. A quit-Safari control must remain stopped. Prototype warm and alarm results do not qualify production timing or persistence.
2. For the separate write run, click **Arm fixture window qualification (120s)** in the confirmed profile's popup; record the UUID and nonce from that arm. This disconnects the probe push port and clears its alarm. The arm is process-local, polls about once per second, and is consumed before the API call; there is no alarm, reboot recovery, automatic rearm, retry of ambiguous writes, or fallback. Close the popup, close **all** Safari windows without quitting, switch to Terminal, and independently record the zero-window precondition. Run once within the arm's lifetime, with separate consent for an attempt that might bring Safari forward or open in the wrong profile:

   ```sh
   "$probe" pull --wait-seconds 10 qualify-window "$PROFILE_UUID" "$INSTANCE_UUID" --allow-fixture-window
   ```

3. During the whole lease, keep the same other app frontmost and observe the desktop independently (e.g., an external screen recording reviewed for transient changes; do not use Apple Events or dispatch). Require `dispatch: "not_called"`, an exact UUID/nonce `claimed` receipt via `qualification_poll`, a same-instance result, `beforeCount: 0`, `afterCount: 1`, `reportedRegularUnfocused: true`, no focus-to-window event, no truncated event evidence, the same Safari process still running, unchanged `frontBefore`/`frontAfter`, and no Safari activation observed. `candidate_observed` deliberately exits nonzero and is **not** a success assertion. After the observation interval, independently inspect the new window: there must be exactly one newly opened regular window with `https://example.com/#safari-probe-created`, in the intended named profile (never B, default, or private), with no permission prompt. Absence of notifications alone is not proof of no activation. A focus change or wrong profile is a failure; a missing/contradictory receipt is inconclusive. Never retry a possibly committed mutation; inspect the fixture and clean up manually after observations are complete.
4. Run fresh attempts with A only enabled and with A/B enabled, target each named profile, and test immediately after closing the last window and late in the warm arm (e.g., 90 seconds after closing within the 120-second budget). Negative controls: use the other UUID, a stale nonce, and an ordinary read-only arm; none may authorize a create. With an ordinary visible window in the qualifying context, qualification must report `window_seen_before_operation` and must not create another window. There is no ambient global window lock; keep the fixture session otherwise idle. Record versions, timings, expected/actual profile, and observations for each run. Do not accept production window creation on source evidence, mocks, a different release, or an unverified profile, focus, or liveness condition.

## Live proof procedure (separate consent required)

Perform only in a consented, disposable macOS GUI session (for CI, a provisioned GitHub-hosted macOS GUI session would need interactive setup; a normal unattended build job is insufficient). Obtain a signed build as above. Register the app by launching the bundle **without** command-line arguments once; the app then exits without opening Safari. With Safari Settings, enable the extension for two explicitly named regular profiles **A** and **B**, and keep private extension access off. Use no Safari web apps. Leave one regular window per profile, with `https://example.com/#safari-probe-a` and `https://example.com/#safari-probe-b` respectively. Do not grant site access until the negative authorization check. From Terminal in the test session, define:

```sh
probe='/absolute/path/to/SafariProbe.app/Contents/MacOS/SafariProbe'
"$probe" discover
"$probe" windows "$A_PROFILE" "$A_INSTANCE"
"$probe" windows "$B_PROFILE" "$B_INSTANCE"
"$probe" inspect "$A_PROFILE" "$A_INSTANCE" "$A_TAB" a
"$probe" add-tab "$A_PROFILE" "$A_INSTANCE" "$A_WINDOW" a
```

Run these commands at the indicated steps, not as an unqualified batch. A timeout is evidence about this attempt, not proof of absence. Do not reuse IDs from another browser session or infer a UUID from window order. Record macOS/Safari versions, signing method, GUI setup, command JSON, observed windows and selected tabs. Record any failure without retrying a possibly successful mutation.

1. **Identity and positive transport.** In each profile's window open the toolbar popup and record the system UUID and the nonce for that visible profile. Choose the extension manually; never use popup data from an unconfirmed window. Close the popup, then run `discover`. Report whether it sees A, B, both, or neither (cold and warm; avoid holding a background inspector open during the primary run). Populate `A_PROFILE`/`A_INSTANCE` and `B_PROFILE`/`B_INSTANCE` from the confirmed identities. Both profiles must be distinct to claim two-profile support. For each, compare the matching native `claimed` receipt and `windows` result with the corresponding UI. If the background reloads, re-identify that profile and record the nonce change.
2. **Negative routing.** For a read-only negative check, call `windows "$A_PROFILE" "$B_INSTANCE"` and verify no grant/result; if both contexts receive the request, A reports `wrong_instance` and B `wrong_profile`. For co-delivery on a write, keep both profiles enabled and communicating, then run the focus test below. A `wrong_profile` receipt from B on **the same** A-targeted mutation proves that B saw that request and the gate denied it; also check that B has no extra tab. No B receipt means no live proof of co-delivery or of B's inability to mutate under the real Safari routing. The synthetic check does not close this gap. If A lists B's visible marker with site access granted, extension window isolation is unproven; do not use the write result for product readiness.
3. **Site authorization.** With `A_TAB` from A's read-only snapshot, set `example.com` to **Deny** manually on the consented test Safari. Invoke `inspect` and expect no DOM success, either because Safari hides the fixture URL or rejects injection. Change the test site to **Allow**, reload the fixture if needed, and rerun on the same intended tab; require a top-frame fixture match and `ok`. Repeat after revocation. `permissionContains` is diagnostic; only the DOM probe is a success signal. Apple's [permission guidance](https://developer.apple.com/documentation/safariservices/managing-safari-web-extension-permissions) says a specific site grant spans profiles in Safari 17+, so this is not a per-profile site-grant test. The fixed script returns only a Boolean for the exact fixture; it does not pin a production read to a document. Apple's [compatibility guide](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility) points to MDN; [browser compatibility data](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json) lists `InjectionResult.documentId` and `InjectionTarget.documentIds` from Safari 18.4. The probe reports whether it actually gets an ID and whether correct and unrelated IDs behave differently on the tested Safari. That observation is not a navigation-race proof.
4. **Existing window/no focus.** With A's marker visible to the extension and B's marker absent from A's snapshot, set `A_WINDOW` to the tested A window ID. Leave another application frontmost (e.g., Terminal), then run `add-tab` as above. Require that only A gains one tab, it opens the fixture and remains unselected, original selected tabs do not change, and Safari never becomes foreground. Check `frontBefore`/`frontAfter`, `activationEvents`, tab/window event recordings and the before/after snapshot against independently observed UI. Repeat with Safari already frontmost but a **different** window selected, launching the command from Terminal using a short scheduled delay in that test session. Verify that the selected window and tab remain unchanged. Output signals are bounded and their absence alone does not prove absence of a transient focus change. If the API reports `created` but UI or activation contradicts it, consider focus behavior failed.
5. **Zero windows.** Use the separate no-dispatch procedure above. The dispatch probe no longer has a window-creation operation.

Prior push observations are not proof for this pull build. The hosted build verifies compilation, packaging, and the synthetic gate; signed live tests are required for App Group access, alarm wake, profile metadata and isolation, focus, and window visibility. Automatic profile creation, permission changes, and live UI testing are not provided or assumed in unattended Actions. Do not enable this probe in MCP or use it as a fallback.
